# Pattern 14: Knowledge Retrieval (RAG)

## What It Is
**Retrieval-Augmented Generation** — enhance LLM responses by first retrieving relevant information from external knowledge bases and injecting it into the prompt as context. Transforms LLMs from "closed-book" to "open-book" reasoners.

## When to Use
- LLM needs access to information beyond training data
- Answering questions about private/proprietary documents
- Need up-to-date or domain-specific information
- Reducing hallucination by grounding in facts
- Building Q&A systems with verifiable, citable responses

## Rule of Thumb
Use when you need an LLM to respond based on specific, up-to-date, or proprietary information not in its training data.

---

## How RAG Works

```
[User Query]
  → Convert to embedding (vector)
  → Search vector database for similar chunks
  → Retrieve top-K relevant snippets
  → Inject snippets into LLM prompt as context
  → LLM generates response grounded in retrieved data
  → [Response with citations]
```

---

## Core Concepts

### Embeddings
- Numerical vector representations of text
- Capture semantic meaning in high-dimensional space
- Similar meanings → vectors close together
- Generated by embedding models (e.g., text-embedding-ada-002, Gecko)

### Chunking
- Breaking large documents into smaller, manageable pieces
- Strategies: by paragraph, by section, by sentence, by token count
- **Critical**: chunking quality directly impacts retrieval quality
- Must preserve context within each chunk

### Vector Database
- Specialized DB for storing and querying embeddings
- Uses algorithms like HNSW for fast nearest-neighbor search
- Options: Pinecone, Weaviate, Chroma, Milvus, Qdrant, pgvector
- Searches by meaning, not keywords

### Retrieval Strategies
| Strategy | Description |
|----------|-------------|
| Vector search | Semantic similarity via embeddings |
| BM25 | Keyword-based ranking (term frequency) |
| Hybrid search | Combine vector + BM25 for best of both |
| GraphRAG | Knowledge graph for relationship-aware retrieval |
| Agentic RAG | Agent reasons about, validates, and refines retrieved knowledge |

---

## RAG Pipeline Steps

1. **Ingestion** (offline): Documents → chunk → embed → store in vector DB
2. **Retrieval** (runtime): Query → embed → search vector DB → get top-K chunks
3. **Augmentation** (runtime): Inject retrieved chunks into prompt
4. **Generation** (runtime): LLM produces grounded response

---

## Advanced: Agentic RAG

Goes beyond simple retrieve-and-inject:
- Agent **reasons** about what to retrieve
- **Validates** retrieved information for relevance
- **Reconciles** contradictions between sources
- Performs **multi-step queries** when first retrieval is insufficient
- Uses **tools** to find missing data

---

## Challenges

| Challenge | Description |
|-----------|-------------|
| Scattered info | Answer spread across multiple chunks/documents |
| Irrelevant retrieval | Wrong chunks retrieved → noise confuses LLM |
| Contradictions | Multiple sources disagree |
| Stale data | Knowledge base not kept up-to-date |
| Latency | Retrieval adds time before generation |
| Pre-processing cost | Entire KB must be chunked + embedded upfront |

---

## Key Implementation Points

1. **Chunk size matters** — too small loses context, too large dilutes relevance
2. **Overlap between chunks** — ensures info at boundaries isn't lost
3. **Metadata enrichment** — attach source, date, section to chunks for filtering
4. **Re-ranking** — after initial retrieval, re-rank by relevance before injection
5. **Citation support** — track which chunks contributed to which response parts
6. **Periodic re-indexing** — keep knowledge base fresh
7. **Evaluate retrieval quality** — measure precision/recall of retrieved chunks

---

## Trade-offs

| Pro | Con |
|-----|-----|
| Grounds responses in facts (reduces hallucination) | Retrieval quality bottleneck |
| Access to private/current information | Requires infrastructure (vector DB, embedding pipeline) |
| Citable, verifiable responses | Latency added by retrieval step |
| No fine-tuning needed for new knowledge | Chunking strategy critically impacts quality |
| Scales to large knowledge bases | Maintenance: re-index as docs change |

---

## Connection to Other Patterns
- **Memory Management** — long-term memory IS the vector store for RAG
- **Tool Use** — retrieval is a tool the agent calls when it needs information
- **Planning** — agent decides WHEN to retrieve vs. use internal knowledge
- **Reflection** — after retrieval, reflect on whether the info is sufficient
- **MCP** — knowledge base can be exposed as an MCP resource
- **Evaluation** — measure RAG faithfulness, relevance, completeness

---

## Anti-Patterns
- ❌ Retrieval without relevance filtering (just inject top-K blindly)
- ❌ Chunks too small (lose context) or too large (dilute signal)
- ❌ No source tracking (can't verify or cite)
- ❌ Stale knowledge base never refreshed
- ❌ Assuming retrieval = correct (retrieved info can still be wrong)

# Interview Depth Extension

> Appended for AI/ML Engineer, Applied AI, and Agent Platform interview prep.
## Interview Answer (60–90s)

RAG retrieves external knowledge and grounds generation to cut hallucination and enable private/current data. Quality hinges on chunking, hybrid retrieval, reranking, and faithfulness checks—not just ‘add a vector DB.’ Agentic RAG lets the model decide what to retrieve and whether it’s enough. Stale indexes and bad chunks create confident wrong answers.

## Deep Dive

### Pipeline
Ingest(chunk, enrich, embed) → retrieve(hybrid) → rerank → pack → generate → cite → faithfulness check.
Agentic: query rewrite, multi-hop, critique sufficiency.

### Failure modes
Irrelevant context, lost-in-middle, contradictions, poisoning, stale docs, citation theater.

### Metrics
Recall@k, nDCG, faithfulness, answer relevance, citation precision, latency.

### When NOT to use
Pure creative tasks; tiny static FAQs better as prompts; when fine-tuned parametric knowledge is enough and fresh.

## Common Interview Questions

**Q1. Why hybrid search?**

A: BM25 catches exact tokens; vectors catch semantics; together more robust.

**Q2. Chunk size?**

A: Trade context vs precision; use overlap + structure-aware splitting.

**Q3. Agentic RAG?**

A: Agent plans retrieval, validates, retries—higher cost, better hard questions.

**Q4. Hallucination with RAG?**

A: Still possible; enforce cite-or-refuse + faithfulness judges.

**Q5. GraphRAG when?**

A: Relationship-heavy corpora; multi-hop entity questions.

**Q6. Eval RAG?**

A: Golden Q/A with labeled passages; faithfulness/relevancy scores.

**Q7. Poisoning?**

A: ACL on ingest, provenance, anomaly detection, signed sources.

**Q8. Memory vs RAG?**

A: Different indexes and write policies; don’t conflate.

## Anti-Patterns

- Blind top-k dump
- No metadata filters
- Never reindex
- Citations without span grounding

## Production Checklist

- [ ] Chunking strategy documented
- [ ] Hybrid + rerank
- [ ] Citation required
- [ ] Freshness SLO
- [ ] Faithfulness eval
- [ ] ACL on corpus
- [ ] Latency budget
